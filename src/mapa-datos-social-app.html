02 recorridos

Elige un dato y sigue su viaje.

Cuatro caminos reales. Las mismas piezas, en distinto orden. Toca una pestaña para cambiar el recorrido.

recorrido 01 · identidad

Entrar sin regalar la sesión.

Better Auth convierte credenciales en una cookie segura. Prisma guarda la identidad; Redis la acelera.

6 pasos
  1. 01
    Cliente · React

    Email + contraseña o «Continuar con Google». Nada sensible se guarda en el navegador.

  2. 02
    Render →Next.js

    POST /api/auth/[...all] entra por HTTPS. Render termina el TLS y lo enruta al contenedor.

  3. 03
    Zod

    Valida el body: formato de email, longitud de contraseña y provider permitido. Si falla, 400 antes de tocar la base.

  4. 04
    Better Auth

    Verifica credenciales u OAuth, crea la sesión y firma una cookie httpOnly + Secure.

  5. 05
    Prisma →Neon

    Escribe User, Account y Session en Postgres con queries tipadas y una transacción.

  6. 06
    Redis +Next.js

    Cachea la sesión, limita intentos fallidos y deja pasar las siguientes rutas.

Resultado: identidad resuelta. Cada request sabe quién eres sin exponer tokens en localStorage.
recorrido 02 · escritura + archivo

Una foto, de la galería al feed.

La imagen va por un camino; los metadatos por otro. Se encuentran en Neon y estallan en el feed por WSS.

6 pasos
  1. 01
    Cliente · React

    Elige foto y caption. El navegador comprime la imagen y pide permiso para subirla.

  2. 02
    Better Auth +Zod

    POST /api/uploads/sign: la sesión se valida y Zod comprueba tipo, tamaño, extensión y caption.

  3. 03
    Supabase SDK

    El servidor firma una URL de subida. La service key nunca sale del contenedor.

  4. 04
    Navegador →Storage

    PUT directo al bucket. La imagen no consume RAM ni ancho de banda de Render.

  5. 05
    Prisma →Neon

    POST /api/posts guarda el post y la ruta del archivo en una transacción.

  6. 06
    Redis +Socket.IO

    Invalida el feed cacheado y emite post:new; el adapter lo reparte a todas las instancias.

Resultado: post publicado y visible al instante para los seguidores conectados.
recorrido 03 · lectura

Abrir el feed en milisegundos.

Redis absorbe la repetición; Neon guarda la verdad. Las imágenes ni siquiera pasan por Render.

6 pasos
  1. 01
    Cliente · React

    Abre /home. Next.js renderiza en el servidor (RSC) el primer feed.

  2. 02
    Better Auth

    Resuelve la sesión desde la cookie. Sin sesión, redirige al login.

  3. 03
    Redis

    GET feed:user:{id}: si hay hit, responde en milisegundos.

  4. 04
    Prisma →Neon

    Si hay miss, consulta posts, autores, likes y comentarios usando índices.

  5. 05
    Redis

    Guarda el resultado con TTL corto (60 s) y sirve el HTML/JSON.

  6. 06
    Supabase CDN

    Las imágenes viajan del CDN de Supabase al navegador, no desde Render.

Resultado: feed rápido y barato. Redis absorbe la repetición; Neon sigue siendo la verdad.
recorrido 04 · bidireccional

Un like que llega a todos.

HTTP escribe el like; Socket.IO lo empuja a la sala del post. Redis hace que todas las instancias se enteren.

6 pasos
  1. 01
    Cliente · React

    Tap en el corazón. La UI cambia al instante (optimistic UI) y envía el like.

  2. 02
    Render →Next.js +Zod

    POST /api/posts/:id/like por HTTPS. Sesión, CSRF y postId validados.

  3. 03
    Prisma →Neon

    Inserta el like de forma idempotente y actualiza el contador.

  4. 04
    Redis

    Refresca contadores y feed cacheado; registra presencia.

  5. 05
    Socket.IO

    La lógica emite like:new a la sala post:{id}.

  6. 06
    Redis adapter →Clientes

    Pub/sub lleva el evento a todas las instancias; los clientes lo reciben por WSS.

Resultado: bidireccional de verdad. HTTP escribe; WebSocket empuja.
03 reglas de oro

Lo que hace que esto funcione.

Neon es la verdad. Redis es la velocidad.

Si Redis se cae, la app sigue funcionando más lenta. Si Neon se cae, no hay app. Redis siempre se puede reconstruir.

La imagen no atraviesa el contenedor.

La subida directa a Supabase con URL firmada ahorra RAM, CPU y ancho de banda en Render. El servidor solo firma y guarda la ruta.

TypeScript se borra al compilar. Zod se queda.

Tipa todo lo que puedas, pero valida en runtime todo lo que entra de fuera: formularios, APIs, env vars y webhooks.

Dos instancias de Render necesitan el adapter de Redis.

Sin pub/sub, cada Socket.IO solo conoce a sus propios clientes. El adapter convierte varias instancias en un solo canal.

en una frase

El navegador pide, Next.js orquesta, Better Auth identifica, Zod valida, Prisma persiste en Neon, Redis acelera y Socket.IO devuelve el cambio a todos.
